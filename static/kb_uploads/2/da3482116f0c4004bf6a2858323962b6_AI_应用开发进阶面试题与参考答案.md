# AI 应用开发进阶面试题与参考答案

这份文档是上一份《`AI_应用开发面试题与参考答案.md`》的进阶版，重点面向：

- 中级到中高级 AI 应用开发岗位
- 有项目经验后的深挖追问
- 系统设计、生产化、调试与评测能力考察

这份文档的问题不再停留在“会不会用”，而是更关注：

- 为什么这么设计
- 出问题时怎么排查
- 方案之间如何取舍
- 如何把 AI 应用做成稳定系统

---

## 一、架构设计与边界

### 1. 你怎么判断一个需求应该做成普通 LLM 问答、RAG、workflow，还是 agent？

**参考答案：**

可以从“外部知识依赖”“流程确定性”“工具调用开放度”三个维度判断：

- 如果只靠模型内知识就能回答，普通 LLM 问答就够了
- 如果依赖私有文档、数据库、知识库内容，优先用 RAG
- 如果步骤大体固定、开发者能明确控制路径，优先用 workflow / graph
- 如果步骤不固定、工具选择开放、需要模型动态规划，才考虑 agent

实际工程里，大多数业务更适合“RAG + workflow”，而不是直接上 agent。

### 2. workflow 和 agent 的边界为什么这么重要？

**参考答案：**

因为二者带来的工程后果完全不同：

- workflow 更可控、可观测、易调试、成本更稳定
- agent 更灵活，但路径不可控、错误更难复现、成本更高

如果本来就能写成确定流程，却硬上 agent，通常会让复杂度和不稳定性上升。

### 3. 你如何设计一个可扩展的 AI 主路由图？

**参考答案：**

设计主路由图时要注意：

- 路由节点只负责识别意图，不做具体业务执行
- capability 节点或子图负责真正完成某类任务
- 把通用字段放到主 state，把局部流程字段留在子图或 capability 中
- 保证新增一个能力时，只需要改路由映射和新增节点，不需要重构全图

常见结构是：

- `route`
- `math capability`
- `weather subgraph`
- `local rag capability`
- `general llm capability`

### 4. 为什么主图和子图的边界要尽量稳定？

**参考答案：**

因为子图一旦设计得太“碎”或太“穿透”，后续会出现：

- 状态字段越来越杂
- 父图和子图高度耦合
- 新增能力时难以复用
- debug 时很难判断问题出在哪一层

稳定边界意味着每个子图负责一个相对完整的业务域流程，而不是只封装一个很小的实现细节。

### 5. 什么样的节点适合独立成 capability，什么样的节点更适合作为内部步骤？

**参考答案：**

适合独立成 capability 的通常是：

- 业务语义完整
- 可以独立测试
- 后续可能复用
- 有自己独立的输入输出边界

更适合作为内部步骤的通常是：

- 只是局部加工
- 只服务于某个 capability
- 单独暴露出来没有业务意义

## 二、LangGraph 进阶

### 6. 你如何设计 LangGraph 的 state，避免后期越来越乱？

**参考答案：**

核心原则是：state 只放“流程共享且后续节点需要依赖”的信息，不要把所有中间变量都塞进去。  
建议按层次设计：

- 输入字段：如 `session_id`、`messages`
- 控制字段：如 `route_decision`
- 业务字段：如 `task`
- 输出字段：如最终结果
- 错误字段：如 `error`、`error_count`

另外，最好把“输入 state”和“运行时 state”区分清楚，减少前端输入和内部状态耦合。

### 7. 为什么 `messages` 常常用 reducer，而 `task` 更常用普通覆盖？

**参考答案：**

因为 `messages` 本质是对话历史，天然是追加型状态，适合 reducer 合并。  
而 `task` 更像当前任务描述，通常新的任务会替换旧任务，所以更适合普通覆盖。

### 8. `interrupt()` 的最大工程价值是什么？

**参考答案：**

最大的价值是把“人工确认/补充输入/审批”变成图执行的一等公民。  
它不仅仅是返回一句提示，而是真正暂停执行、保存执行现场、等待恢复。

这会让以下场景更自然：

- 删除前确认
- 调外部工具前确认
- 缺参时让用户补充
- 审批流

### 9. `interrupt()` 的最大坑是什么？

**参考答案：**

最大坑是：恢复时节点会从头重放。  
如果节点在 `interrupt()` 前做了有副作用的事，比如：

- 写数据库
- 调外部 API
- 发消息
- 写日志并依赖幂等

那恢复时可能重复执行，所以必须做好副作用隔离和幂等控制。

### 10. 如何避免 interrupt 节点恢复时重复副作用？

**参考答案：**

常见做法：

- 在 `interrupt()` 前不要做外部副作用
- 把副作用放到 `interrupt()` 后的独立节点
- 对外部写操作做幂等键
- 用状态字段标记“是否已执行”

### 11. 什么时候应该用 `Command(goto=...)`，什么时候用条件边？

**参考答案：**

条件边适合图结构层面的静态分支，逻辑比较清晰固定。  
`Command(goto=...)` 更适合在节点内部根据运行时结果动态决定下一步，尤其在：

- interrupt 恢复后
- 某节点内部已经拿到了充分决策信息
- 不想额外拆一个 route 函数

### 12. 你如何理解 `astream_events()` 在生产调试中的价值？

**参考答案：**

`astream_events()` 的价值在于它不是只给你最终结果，而是把执行过程拆成可观察事件。  
这对排查下面这些问题特别有用：

- 路由走错了
- 某个节点耗时异常
- tool 没调用成功
- 中断发生在哪一步
- 某个模型请求失败或输出不符合预期

它是 graph tracing 的关键工具。

## 三、RAG 进阶

### 13. 一个 RAG 系统效果差，你会优先排查哪几层？

**参考答案：**

通常按三层排查：

1. 文档层：清洗、切块、metadata 是否合理
2. 检索层：embedding、召回、filter、topK、rerank 是否合理
3. 生成层：prompt、上下文拼接、引用方式是否合理

不要一上来就怪模型，经常问题在更前面。

### 14. 怎么判断是“chunk 方案有问题”，还是“embedding 模型不行”？

**参考答案：**

如果相同 query 在人工看来能命中相关段落，但检索出来的 chunk 经常碎、上下文断裂、标题和正文被分离，那更可能是 chunk 问题。  
如果 chunk 语义边界已经很合理，但仍然长期召回不到语义相近内容，那才更像 embedding 或检索策略问题。

### 15. 在知识库问答里，为什么 metadata schema 的设计要尽早做？

**参考答案：**

因为 metadata 一旦随意设计，后面会直接影响：

- 过滤能力
- 多租户隔离
- 权限控制
- 删除重建
- 结果来源展示
- 评测统计

如果前期不统一 schema，后期很难补。

### 16. 什么时候需要 query rewrite，什么时候不值得做？

**参考答案：**

需要 query rewrite 的典型情况：

- 多轮对话省略主语
- 用户表达口语化
- 文档术语和用户提问用词不一致
- 查询过短或过泛

不太值得做的情况：

- 用户问题本身已经非常明确
- 查询是精确术语检索
- 系统整体延迟预算非常紧张

### 17. rerank 的收益和代价分别是什么？

**参考答案：**

收益：

- 排序更准
- 降低把不相关 chunk 拼进 prompt 的概率
- 提升最终回答质量

代价：

- 增加额外模型调用成本
- 增加延迟
- 增加系统复杂度

所以通常适合“先 recall，再对候选集 rerank”，而不是对全量内容做重排。

### 18. 你如何设计“文件删除后删除对应向量”的机制？

**参考答案：**

必须给每个 chunk 打上稳定的 metadata，比如：

- `file_id`
- `file_name`
- `chunk_index`

删除时基于 `file_id` 做过滤删除，而不是依赖文本本身去猜。  
同时建议在 MySQL 中记录索引状态，失败时可以补偿重试。

## 四、Agent / Tool Calling 进阶

### 19. tool calling 最大的工程挑战是什么？

**参考答案：**

最大的挑战不是“会不会调用”，而是“调用是否稳定可控”。  
常见挑战包括：

- 参数提取不稳定
- 工具选错
- 工具结果格式不统一
- 工具失败后的恢复机制不完善
- 多工具调用链路难排查

### 20. 你如何设计工具返回值，才能更稳定地被模型消费？

**参考答案：**

工具返回值最好：

- 结构清晰
- 字段稳定
- 尽量机器可解析
- 不要混入太多无关描述

例如优先返回：

```json
{
  "city": "上海",
  "weather": "多云",
  "temperature": "26C"
}
```

而不是一大段风格化描述文本。

### 21. planner-executor 模式适合什么问题？

**参考答案：**

适合：

- 任务较复杂，不能一步完成
- 先规划再执行能提升稳定性
- 多步工具调用有明显顺序
- 希望把“思考”和“执行”分开

但如果问题本身很简单，planner-executor 反而会增加成本和延迟。

### 22. supervisor + 多专家模式的风险是什么？

**参考答案：**

风险主要有：

- 系统复杂度急剧上升
- 调试困难
- token 成本上涨
- 多代理之间信息传递损耗
- 责任边界不清

所以多智能体不是“更高级”，而是“更复杂”，只有在确实需要时才值得用。

## 五、LangServe / API / 流式能力

### 23. 为什么 wrapper runnable 很容易把原生 graph 能力包坏？

**参考答案：**

因为 wrapper 常常会做这些事情：

- 改输入 shape
- 改输出 shape
- 在内部只调用 `ainvoke`
- 把 graph 的流式行为包成普通返回值

这样会导致：

- 原生 `stream/stream_events` 失真
- interrupt 信息被隐藏
- 调试链路多一层

### 24. 什么时候应该直接暴露 graph，什么时候应该包一层 wrapper？

**参考答案：**

直接暴露 graph 适合：

- 想保留原生 LangServe graph 能力
- 需要 `/stream`、`/stream_events`
- 输入 schema 本身已经合理

包 wrapper 适合：

- 想统一前端协议
- 想隐藏 `Command(resume=...)`
- 想把 resume、thread_id、格式转换封装起来

### 25. 为什么 `input_type` 设计不好，会引发很多奇怪问题？

**参考答案：**

因为 `input_type` 会影响：

- 请求校验
- LangServe 解包逻辑
- 下游 runnable 接收到的数据 shape

一旦它和真实 runnable 预期不一致，就会出现：

- 少字段
- 字段嵌套错层
- list 和 dict 混用
- graph 起点拿不到正确 state

## 六、评测与观测

### 26. 一个 AI 应用为什么不能只看最终回答对不对？

**参考答案：**

因为最终回答只是最后结果，无法告诉你问题出在哪一层。  
AI 应用通常是多阶段系统，问题可能出在：

- 路由错
- 检索错
- 工具错
- prompt 错
- 模型错

所以必须把过程可观测化。

### 27. 你会统计哪些核心指标？

**参考答案：**

建议至少统计：

- 请求总耗时
- 每节点耗时
- LLM 调用次数
- token 用量
- cost
- tool 失败率
- route 命中分布
- interrupt 次数
- resume 成功率

### 28. 如何区分 tracing、logging、metrics？

**参考答案：**

- logging：记录文本日志，方便查单点事件
- metrics：记录可聚合指标，方便看趋势和告警
- tracing：记录一次请求的完整链路，方便还原执行过程

三者是互补关系，不是替代关系。

### 29. AI 应用的回归测试为什么比普通 CRUD 更难？

**参考答案：**

因为模型输出有非确定性，同样输入不一定每次字面一致。  
所以不能只做精确字符串比对，而要设计：

- 结构化断言
- 规则断言
- rubric 评测
- 关键字段断言
- 结果区间判断

## 七、成本与性能优化

### 30. 成本优化时，哪些地方最值得优先下手？

**参考答案：**

通常优先考虑：

- 减少不必要的模型调用
- 控制 prompt 长度
- 控制检索结果数量
- query rewrite / rerank 做按需触发
- 用便宜模型做路由和分类
- 做缓存

### 31. 为什么“便宜模型做路由，强模型做生成”是常见方案？

**参考答案：**

因为路由、分类、参数提取这类任务通常更结构化，对模型创造性要求低，用便宜模型就能做得不错。  
而最终生成、复杂推理、工具规划更依赖模型能力，才值得用更强模型。

### 32. AI 应用的性能瓶颈通常在哪？

**参考答案：**

常见瓶颈有：

- 外部 LLM 接口
- embedding 批处理
- rerank 模型
- 向量检索
- 大文件处理
- 同步阻塞操作

性能优化不能只看代码，还要看系统链路。

## 八、安全与权限

### 33. prompt injection 在 RAG 场景里为什么更危险？

**参考答案：**

因为外部文档本身也可能携带恶意提示。如果系统直接把检索到的文本拼进 prompt，又不做隔离或约束，模型可能会被文档内容误导。  
所以 RAG 场景不仅要防用户输入注入，还要防知识库内容注入。

### 34. 多租户 AI 系统里，metadata filter 为什么不只是“优化手段”，也是“安全手段”？

**参考答案：**

因为如果没有租户级过滤，用户可能检索到不属于自己的文档。  
这不只是检索精度问题，而是权限越权问题。  
所以像 `tenant_id`、`project_id`、`access_scope` 这类字段必须在检索前就参与过滤。

### 35. 工具调用为什么也有安全风险？

**参考答案：**

因为一旦工具能：

- 查数据库
- 发请求
- 改配置
- 删除数据

那模型错误调用、越权调用、参数污染都会变成真实业务风险。  
所以工具应该有权限边界、输入校验、幂等控制和审计日志。

## 九、数据库与一致性

### 36. 如果文件上传成功了，但向量入库失败了，你怎么处理？

**参考答案：**

不能依赖单事务解决，因为 MySQL、文件系统、向量库不是同一个事务域。  
更稳的做法是：

- 先记录文件状态为 `uploaded`
- 后台异步做索引
- 成功后改成 `indexed`
- 失败时记录 `failed` 和错误信息
- 支持重试

这是典型的最终一致性方案。

### 37. 为什么“删文件、删 MySQL、删向量库”通常要做成任务而不是接口内一步完成？

**参考答案：**

因为这涉及多个系统：

- MySQL
- 文件系统
- 向量数据库

任何一步失败都可能导致不一致。做成任务后更方便：

- 记录状态
- 重试
- 补偿
- 审计

## 十、真实项目追问

### 38. 你当前项目里为什么会从 `pending_action` 迁移到 `interrupt()`？

**参考答案：**

因为 `pending_action` 属于应用层手写状态机，虽然能工作，但需要：

- 自己维护 pending 状态
- 自己恢复路由
- 自己处理确认分支

而 `interrupt()` 是 LangGraph 原生能力，更贴合“暂停并恢复”的语义。  
迁移后的好处是流程更自然，但也引入了 checkpointer、thread_id、resume 这些配套要求。

### 39. 你在项目里踩过哪些 `invoke / ainvoke / stream / astream_events` 的坑？

**参考答案：**

典型坑包括：

- 把 `astream_events()` 当普通协程 `await`
- wrapper 吃掉 graph 原生流式行为
- input schema 和实际 shape 不一致
- interrupt 返回没有按预期暴露给前端

这些问题本质都和“输入输出 shape”“同步异步边界”“流式抽象”有关。

### 40. 如果现在要把这个项目做成“可上线版本”，你优先补哪三块？

**参考答案：**

我会优先补：

1. 会话与 checkpoint 持久化
2. tracing / token / latency / error 观测
3. 文件入库、索引、删除的异步任务化

因为这三块最直接决定系统是否稳定、可排查、可维护。
